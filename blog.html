从 HTTP 到一个真正上线的网页

这次计算机网络实验，我把自己做的东西放到了公网上，也顺带把浏览器和服务器 之间发生了什么看了个大概。这篇文章是做完之后的一点整理，顺便把过程记下来， 免得以后要重做一遍。

本文目录

  1. 为什么网页访问离不开 HTTP
  2. HTTP 从 1.1 到 2 再到 3
  3. HTML 和 CSS 各自负责什么

一、为什么网页访问离不开 HTTP

在浏览器地址栏里敲下一个网址并回车，我们看到的是一张页面，但背后发生的事情要具体得多。 浏览器首先要通过 DNS 把域名翻译成 IP 地址，然后和服务器建立连接，接着发出一个 HTTP 请求。这个请求里包含请求方法（比如 GET）、 请求的路径，以及一堆头部字段，用来告诉服务器我是谁、我能接受什么格式的内容。

服务器收到请求后，返回一个响应：一个状态码，加上响应头和响应体。 状态码 200 表示一切正常，404 表示这个资源根本不存在。 平时我们打开网页时看到的每一个文字、每一张图片、每一个样式文件，都是一次独立的 HTTP 请求换回来的。

打开开发者工具的 Network 面板刷新一下就能看到，一个看起来很简单的页面， 背后也有几十条请求在跑。

二、HTTP 从 1.1 到 2 再到 3

HTTP 的版本演进一直在解决同一个问题：怎么少等一点。

HTTP/1.0 默认使用短连接，每请求一个资源就要重新建立一次 TCP 连接， 代价很高。HTTP/1.1 改成了默认持久连接，一次连接可以复用给多个请求， 还引入了 Host 头字段，让同一台服务器可以托管多个域名。它至今仍是被 使用得最多的版本。但 1.1 有个绕不过去的毛病：虽然请求可以一次发出去多个， 响应却必须按顺序回来，前面那个慢了，后面全都要排队，这就是所谓的队头阻塞。

HTTP/2 用二进制分帧和多路复用解决了应用层的排队问题， 一个连接上可以并行跑很多个请求，头部压缩也省下了不少重复传输的开销。 但它的多路复用是建在 TCP 之上的，而 TCP 要求数据严格按顺序到达 —— 一旦丢包，所有流都得等着重传，排队从应用层挪到了传输层。

HTTP/3 的做法最干脆：换掉 TCP，改用基于 UDP 的 QUIC 协议。 每个流独立传输，丢包只影响那一条流；同时它把加密握手集成进来，支持 0-RTT， 连接迁移也让网络切换时连接不再中断。

这个网站的线上版本部署在 GitHub Pages 上，实测用的是 HTTP/2。

三、HTML 和 CSS 各自负责什么

这个页面里，HTML 管结构和内容：哪一段是标题、哪一块是列表、 哪里是导航、哪里是页脚，它回答的是「这块东西是什么」。 CSS 管外观：颜色、间距、字号、怎么排列，回答的是「它长什么样」。

这个分工听起来像句废话，代码多起来之后才显出好处。整站的样式都放在 css/style.css 一个文件里，主色、圆角、阴影定义成 CSS 变量。 深色模式就是把变量重新赋一遍值，没有另外写一套样式表。 如果样式是散在标签属性里写的，改这一处会非常难受。

布局主要用了 Flexbox 和 Grid。导航栏和按钮 用 Flex 排，卡片区域用 Grid 配合 auto-fit 和 minmax()，屏幕窄了会自己换行，不用给每种宽度单独写一套规则。

四、把网页部署到 GitHub Pages

网页写完还只是躺在自己电脑上的几个文件，只有放到公网服务器上，别人才访问得到。 GitHub Pages 提供了一种很轻的静态托管方式：把文件推到仓库里，它就帮你当成网站发布。

整个过程大致是这几步：

git init
git add .
git commit -m "init website structure"
git remote add origin https://github.com/<用户名>/<用户名>.github.io.git
git push -u origin main

推到仓库之后，在仓库设置里把 Pages 的发布分支指向 main， 等上一两分钟，访问 https://<用户名>.github.io 就能看到自己的页面了。 之后再改内容，只要重新提交并推送一次，线上就会更新。

静态网站没有后端。服务器只是把已经生成好的 HTML、CSS、图片原样发回来， 不执行任何代码。好处是快、不容易被攻击；代价是做不了登录、评论这类 需要服务端参与的功能。个人主页用不上这些，这个取舍是划算的。

五、这次实验的收获

这个网站的代码不是我逐行手写的。结构怎么分、每个区域放什么、配色和交互做成什么样， 这些是我定的；具体的 HTML / CSS / JavaScript 有相当一部分借助 AI 工具生成， 我再逐段读、逐处改。

这么做的收获和纯手写不太一样。手写的时候卡住的多半是语法和布局；这次主要花在 「看懂」上：为什么这里用 Grid 而不是 Flex、表格在手机上为什么要改成堆叠布局、 深色模式为什么只改几个变量就够了。看不懂的地方就回去翻文档。

HTTP 那部分是实打实自己动手查的。强制请求 HTTP/2 拿到 h2、再退回 1.1 对比结果， 才把「协议协商」这件事弄明白。之前它对我来说只是要背的状态码和字段名。

另外，写网页比看上去琐碎。同一个布局在不同宽度下表现可能完全不一样， 一个很小的间距问题，背后往往是盒模型或者对齐方式没弄对。 这个页面还有不完善的地方，但它确实在互联网上跑着。
