HTTP 协议版本演进：从 1.0 到 HTTP/3

发表于2026-10-03|更新于2026-10-08|计算机网络
|浏览量:

打开一个网页，浏览器和服务器之间到底聊了些什么？这篇文章梳理 HTTP 协议从 1.0 到 HTTP/3
的演进脉络 —— 每一代版本都在解决上一代暴露出来的同一个问题：等待。

一张表看懂四代版本

版本 传输层 连接方式 核心改进 遗留问题
HTTP/1.0 TCP 短连接 引入状态码、请求方法、头部字段 每次请求都要重新握手，效率低
HTTP/1.1 TCP 持久连接 Host 头、增强缓存、分块传输、范围请求 应用层队头阻塞
HTTP/2 TCP 单连接多路复用 二进制分帧、头部压缩、服务器推送 传输层队头阻塞
HTTP/3 QUIC（UDP） 流独立传输 0-RTT 握手、连接迁移、默认加密 生态仍在完善

HTTP/1.0 —— 奠基的一代

HTTP/1.0 确立了今天我们熟悉的基本概念：

  • 状态码：200 表示成功，404 表示资源不存在，500 表示服务端出错
  • 请求方法：GET 取资源，POST 提交数据
  • 头部字段：Content-Type 告诉对方我发的是什么格式

它最大的问题是默认短连接 —— 每请求一个资源（一个 HTML、一张图、一个 CSS），
都要重新建立一次 TCP 连接。三次握手 + 四次挥手，纯粹是在等待。

HTTP/1.1 —— 用得最多的一代

直到今天，大量网站依然跑在 HTTP/1.1 上。它的关键改进：

1. 持久连接（默认开启）
一次 TCP 连接可以复用给多个请求，省掉了反复握手的开销。

2. Host 头字段
有了它，同一个 IP 上可以托管多个域名（虚拟主机）。在此之前，
服务器没法知道浏览器到底想访问哪个网站 —— 这也是 HTTP/1.0 时代 IP 地址不够用的原因之一。

3. 更强的缓存控制
Cache-Control、ETag、If-None-Match 让浏览器可以精确判断”这个资源还能不能用本地的”，
不再需要每次都问服务器。

4. 分块传输与范围请求
Transfer-Encoding: chunked 支持流式传输，不用等整个资源准备好；
Range 请求支持断点续传，下载大文件时特别有用。

遗留问题：管线化的队头阻塞

HTTP/1.1 允许一次性把多个请求发出去（管线化），但响应必须按顺序返回。
如果第一个请求处理很慢，后面所有响应都得排队等着 —— 这就是队头阻塞（Head-of-Line Blocking）。
所以浏览器实际上很少真的用管线化，而是开 6 个左右的并发连接来绕过它。

HTTP/2 —— 解决应用层的排队问题

HTTP/2 的核心目标就是干掉应用层的队头阻塞：

  • 二进制分帧：不再用文本传输，改成二进制帧，解析更高效、更不容易出错
  • 多路复用：一个 TCP 连接上并行跑多个请求流，互不阻塞
  • 头部压缩（HPACK）：HTTP 头部有大量重复字段（Cookie、User-Agent……），压缩后能省不少流量
  • 服务器推送：服务端可以主动把客户端马上要用的资源推过去
  • 流优先级：客户端可以告诉服务器哪些请求更着急

遗留问题：传输层的队头阻塞

HTTP/2 把多路复用建在 TCP 之上，而 TCP 本身要求数据严格按序到达。
一旦某个数据包丢了，后面所有流的数据都得在内核缓冲区里等着重传 ——
应用层不排队了，传输层还在排队。

HTTP/3 —— 换掉 TCP

HTTP/3 的答案很直接：既然 TCP 是瓶颈，那就换掉它。

它基于 QUIC 协议，跑在 UDP 之上：

  • 彻底解决队头阻塞：QUIC 的流是独立传输的，丢包只影响丢包的那一条流
  • 极速连接：集成了 TLS 1.3，握手和加密协商合并，支持 0-RTT / 1-RTT
  • QPACK 头部压缩：针对 QUIC 重新设计的头部压缩方案
  • 连接迁移：靠连接 ID 而不是 IP 来标识连接 —— 从 WiFi 切到 4G 时连接不会断
  • 默认加密：QUIC 强制加密，安全性更好

代价是 UDP 在某些网络环境下会被中间设备限制，所以 HTTP/3 通常和 HTTP/2 并存，
由浏览器自动选择。

总结

回顾整条演进路线，每一代都在回答同一个问题：如何减少等待。

代际 回答的方式
HTTP/1.0 → 1.1 别每次都重新握手
HTTP/1.1 → 2 别在应用层排成一队
HTTP/2 → 3 别让传输层的丢包拖累所有请求
